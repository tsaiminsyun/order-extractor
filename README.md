# 訂單擷取（Amazon.co.jp / 楽天市場 / Shopify / タワーレコード / ポケモンセンター / にじさんじ / アニメイト / mu-mo / ZOZOTOWN / plusmember / ちいかわくじ）

Chrome 擴充功能（Manifest V3），從訂單列表頁擷取配送中的訂單，匯出 JSON。

支援 Amazon.co.jp、楽天市場、タワーレコード、ポケモンセンターオンライン、にじさんじオフィシャルストア、アニメイト通販、mu-mo ショップ、ZOZOTOWN、plusmember、ちいかわくじ，以及**任何 Shopify 商店**。Shopify 那一層是用頁面特徵判斷的，
不是網域白名單 —— 代購常用的 ちいかわマーケット、ナガノマーケット、各家官方周邊店等十幾個站都走同一套。

供代購 / WMS 流程使用，所以取捨偏向**寧可留空，不要抓錯**：認不出來的欄位一律空著，不猜。

## 安裝

1. Chrome 開啟 `chrome://extensions`
2. 開啟右上角「開發人員模式」
3. 「載入未封裝項目」→ 選擇本資料夾

載入後 popup 標題旁會顯示版本，可確認是不是最新的那一份。

## 使用

1. 登入後開啟訂單列表頁：
   - Amazon：https://www.amazon.co.jp/gp/css/order-history
   - 楽天：https://order.my.rakuten.co.jp/purchase-history/order-list/
   - Shopify 商店：該店的 `/account`（例如 https://chiikawamarket.jp/account）。
     多語系商店的路徑會帶語系前綴，例如 `/zh-hant/account`、`/zh-hans/account`、`/en/account`，都支援
   - タワーレコード：會員頁的注文履歴（`tower.jp/ec/…`）。這個站台**只有列表頁、沒有注文詳細頁**，
     所以一頁就擷取得完。認的是版面特徵不是固定網址，頁面路徑改了也還能用
   - ポケモンセンターオンライン：會員頁的注文履歴（`www.pokemoncenter-online.com`）。一樣認版面特徵
     （訂單列表 `.comOrderList` 裡有連到 `/order-details/` 的連結），不寫死路徑。
     這個站台跟 Shopify 商店一樣不在 manifest 的網址清單裡，點圖示時才由 popup 注入
   - にじさんじオフィシャルストア：https://shop.nijisanji.jp/mypage/order-history 。一樣認版面特徵
     （`.order-history-list` 裡有連到注文詳細頁的連結），也一樣是點圖示時才注入
   - アニメイト通販：https://www.animate-onlineshop.jp/mypage/history.php 。跟タワーレコード一樣**一頁就有全部欄位**，
     只有翻頁時才多讀一頁。點圖示時才注入
   - mu-mo ショップ：https://shop.mu-mo.net/avx/sv/mypordhist05?jsiteid=mumo （購入履歴・配送状況一覧）。點圖示時才注入
   - ZOZOTOWN：會員頁的注文履歴（`default.html`）。認版面特徵（`.orderList` 裡有連到 `detail.html?oid=` 的連結），
     不寫死路徑。點圖示時才注入
   - plusmember：`store.plusmember.jp` 會員頁的購入履歴。認版面特徵（`.list` 的訂單列裡有「詳細」），不寫死路徑。點圖示時才注入
   - ちいかわくじ：https://online-kuji.chiikawamarket.jp/mypage/history （購入履歴）。列表是前端畫出來的，**等卡片出現再點圖示**。
     每張卡片要在隱藏 iframe 裡點開才讀得到，比其他站台慢（一張幾秒）。點圖示時才注入
2. 點擴充功能圖示 —— **一打開就跑完**，表格上就是結果
3. 取消不要的列，按「下載 JSON（N 筆）」（檔名會帶站台，例如 `amazon-orders-20261006-0930.json`）

## 功能與需求

這個擴充功能只要**配送中**的訂單：已經出貨、還沒送到的包裹。

| 需求 | 做法 |
| --- | --- |
| 點圖示就顯示 | popup 一打開就整套跑完：掃描列表 → 讀配送資料 → 顯示。中間不用再按任何按鈕 |
| 只顯示七天內、有 tracking ID 的訂單 | 超過七天的不列，也沒有開關叫得出來；沒有 tracking ID 的包裹也不列 |
| 能排除已到貨就排除 | 認得出送達狀態的站台直接擋掉（見下方「只擷取配送中的訂單」） |
| 這一頁都在七天內就自動翻下一頁 | 看到第一筆超過七天的訂單就停 |
| 表格：訂單編號 / 品名 / 合計 / 物流業者・運單號 | 一個包裹一列，品名一件一行 |
| 可以勾選，按下就直接下載 | 預設全勾，按「下載 JSON」只下載勾選的那幾列 |

### 七天

**只列出七天內下單的訂單**（含今天）。七天是「配送中」的替代條件：
Shopify、ポケモンセンター、plusmember、ちいかわくじ 與楽天英文介面讀不到送達狀態，七天前下的單多半已經到貨了。
定義在 [main.js](src/content/main.js) 的 `RECENT_DAYS`，popup 不自己算日期。

超過七天的訂單**連詳細頁都不讀** —— 讀了也不會列出來。
ちいかわマーケット 一頁 10 筆、七天內只有 2 筆的話，就只讀 2 次詳細頁。

注文日讀不到的（少見語系）**當成「不確定」，照樣列出來但不預設勾選** ——
它不是「七天前的」，只是算不出來。站台改版導致日期抓不到時，訂單不該整批無聲消失。

### tracking ID

只列有 tracking ID 的包裹。配送中卻讀不到 ID 的（例如 Amazon 的配送狀況頁被擋下）不列，
但狀態列會寫出有幾個 —— 不讓它無聲無息地消失。

### 自動翻頁

翻頁停在下列任一條件（[main.js](src/content/main.js) 的 `scanOrders`）：

| 停止條件 | 為什麼 |
| --- | --- |
| 這一頁出現超過七天的訂單 | 訂單列表都是新到舊排的，看到第一筆舊的就表示界線過了，下一頁只會更舊 |
| 找不到下一頁 | 站台沒有分頁，或認不出它的分頁長怎樣 |
| 翻到的頁面沒有新的注文番号 | 重複或空頁（Shopify 翻過頭就是空的） |
| 翻到第 10 頁（`MAX_PAGES`） | 保險閥，分頁連結壞掉時不要一直翻下去 |

「超過七天」看的是**每一筆**訂單，包括已送達、沒有伝票番号這些不擷取的。
各站台對那些訂單回傳「空的訂單」而不是直接丟掉，就是為了留下它的注文日 ——
不然七天的界線剛好落在一串已送達的訂單上時，會白翻下一頁。

翻幾頁會寫在狀態列上。翻頁失敗不算錯誤，把已經掃到的交出去就好。
另外載入的列表頁跟詳細頁走同一套：伺服器渲染的用 `fetch`，前端渲染的用隱藏 iframe，一樣不開新分頁。

popup 關掉再打開時，content script 若還在跑上一次，就接著等那一次的結果，不會再開一批 iframe。

### 注文日的來源

| 站台 | 注文日的來源 |
| --- | --- |
| Amazon | 標頭的「注文日 / Order placed / 已下订单」欄 |
| 楽天 | 「注文日：」標籤旁的 `2026/09/18(金)` |
| Shopify | `<time datetime="2026-10-05T14:53:07Z">`。先讀顯示的文字（商店時區的日期），認不得才用 `datetime`（UTC，凌晨下的單會差一天） |
| タワーレコード | `.deliveryAbout` 的「注文日」欄 |
| ポケモンセンター | 列表頁的 `.time`：`2026年09月 10日（木）`（月和日中間有空格） |
| にじさんじ | 列表頁的 `.order-history-date`：`2026年07月22日 19:48` |
| アニメイト | 列表頁的 `.order__date`：`注文日　2026/09/18` |
| mu-mo | 列表頁每筆訂單的標頭：`▼P 2026/10/06ご注文（履歴詳細）` |
| ZOZOTOWN | 列表頁的 `td.orderTime`：`注文日：2026.10.17`（點分隔） |
| plusmember | 列表頁的 `li.time`（購入日時）：`2026/05/19 13:50` |
| ちいかわくじ | **詳細頁**的「購入日時」：`2024/12/07 14:31`。列表頁上沒有日期，要一張一張點開才知道（見「ちいかわくじの錨點」） |

各站台寫法都不一樣，一律由 [util.js](src/content/util.js) 的 `parseDate` 轉成 `YYYY-MM-DD`。
認不得的格式回 `null`，不猜 —— 猜錯會讓使用者漏抓或多抓。

## 為什麼一定要多讀一頁

兩邊都試過只靠列表頁完成擷取，結論是**不行**，缺的欄位列表頁根本沒有。
實際頁面存在 [tests/fixtures/](tests/fixtures/)，查證寫成了測試（[amazon-real.test.cjs](tests/amazon-real.test.cjs) 第 3 項）。

| 站台 | 列表頁缺什麼 | 查證 |
| --- | --- | --- |
| ちいかわくじ | 全部：購入番号、日期、配送業者、伝票番号、獎品、金額 | 列表頁的卡片只有くじ名、回數、狀態與圖片，**連連結都沒有** |
| plusmember | 配送業者、お問い合わせ番号、商品、個数 | 列表頁只有購入日時、購入店舗、注文番号、お支払い方法、合計金額，連配送狀態都沒有 |
| Amazon | 配送業者、トラッキングID | 日 / 英 / 簡中三份完整列表頁裡都搜不到追蹤號碼、業者名稱或任何標籤字樣，連內嵌 JSON 也沒有；列表頁只給得出配送狀況頁的連結（帶 `shipmentId`） |
| ZOZOTOWN | 伝票番号、合計 | 列表頁的「追跡する」只打開配送歷程視窗，沒有伝票番号 |
| mu-mo | 配送会社、伝票番号、全部商品、個数、合計 | 列表頁只有注文番号、注文日、商品摘要、配送先、配送状況 |
| にじさんじ | 配送伝票番号、合計、数量 | 列表頁只有注文番号、注文日、品名 / 画像、每件商品的狀態標籤 |
| ポケモンセンター | 送り状番号、合計、第二件以後的商品 | 列表頁只有注文番号、注文日、出貨進度、第一件商品與「含む4点」這種件數 |
| 楽天 | 合計 | 列表頁只有各商品單價，沒有「支払い金額」。單價加總在免運又沒用折價券時剛好相等，但送料、折價券、點數都會讓它對不上，不能當合計 |

タワーレコード與アニメイト則相反：列表頁上什麼都有（連商品圖與伝票番号都在），所以**一頁都不用多讀**。

所以「配送中的包裹」（Amazon）與「要擷取的訂單」（楽天）各需多讀一頁。程式會盡量少讀：

- Amazon 只讀有「配送状況を確認」按鈕的包裹，同一個包裹的多件商品共用一次讀取
- 楽天在日文介面的列表頁就看得出哪些訂單沒有伝票番号，那些連詳細頁都不會載入
- ポケモンセンター只讀進度是「発送済み」的訂單（注文受付済み / 発送準備中的不讀）
- にじさんじ的商品全部「着荷済み」的訂單不讀
- mu-mo 列表上配送状況是「出荷待ち」或「配達完了」的訂單不讀
- ZOZOTOWN 所屬包裹全部「配達完了」的訂單不讀
- plusmember 的列表頁看不出寄出了沒，七天內的每一筆都要讀（跟 Shopify 一樣）
- ちいかわくじ 由新到舊一張一張點開，點到第一張購入日時超過七天的就停（那一張不再點配送情報）

## 只擷取配送中的訂單

**配送中 ＝ 已出貨、還沒送達。** 已送達的不擷取 —— 那批貨已經到倉，不必再追。

| 站台 | 怎麼判斷 | 為什麼這樣判斷 |
| --- | --- | --- |
| Amazon | 包裹的狀態文字不是「お届け済み / Delivered / 已于…送达」（`.yohtmlc-shipment-status-primaryText`） | 送達之後「配送状況を確認」按鈕**還會留著**，光看按鈕分不出在途或已送達 |
| 楽天 | 配送進度列的目前狀態（`[class*="item-shipping-active--"]`）不是最後一步 | 進度是 ショップ → 出荷 → 配達店 → 配達完了（繁中：店家 → 出貨 → 配送據點 → 配送完成），走到最後一步就是已送達 |
| Shopify | 商品有追蹤號就算 | Shopify 的訂單狀態只有「未出貨 / 部分出貨 / 已出貨」，**沒有送達狀態** |
| タワーレコード | 出荷表示（`.deliverySt`）沒有「（受取済）」 | 在途是「2026/10/09 に出荷しました」，送達後變成「2026/08/09 に出荷しました（受取済）」 |
| ポケモンセンター | 出貨進度是「発送済み」（`.comReceiptBox` 帶 `.sent`，或目前這一步 `.finish` 是最後一步） | 進度只有 注文受付済み → 発送準備中 → 発送済み，**沒有送達狀態** |
| ZOZOTOWN | 包裹的目前狀態（`.orderDetailHeader-h`）不是「配達完了」，而且進度列（`data-step` / `data-max-step`）沒走到最後一步 | 這裡比對文字是安全的：那個標籤只放目前的狀態，不是進度列上那一串步驟名稱。9 月以前的包裹沒有進度列，只能看標籤 |
| mu-mo | 列表的配送状況不是「出荷待ち」/「配達完了」；詳細頁再逐個包裹看配送狀況格的第一行是不是「配達完了」 | 配送中的字樣還沒看過（實際頁面只有這兩種），所以反過來：確定沒東西在路上的才跳過，其餘一律讀詳細頁 |
| アニメイト | 進度列（`.order-tracking__timeline`）的目前這一步 `li.current` 不是最後一步 | 進度是 注文受付 → お支払い → 商品準備中 → 出荷作業中 → お届け済。跟楽天一樣，「お届け済」是最後一步的名稱、每一筆都看得到，所以只能用結構判斷 |
| ちいかわくじ | 配送情報有伝票番号就算 | 狀態只看過「発送されました」：2025 年 5 月寄出的包裹現在也還是，**沒有送達狀態** |
| plusmember | 詳細頁有お問い合わせ番号就算 | 詳細頁的狀態（「支払ステータス」）只到「発送完了」，**沒有送達狀態** |
| にじさんじ | 每件商品的狀態標籤（`.label-list .label`）不是全部「着荷済み」 | 標籤的 class 都是 `label-gray`，只能比對文字。2022 年的訂單到現在還是「出荷済み」，不是每筆都會更新成着荷済み —— 舊訂單本來就被七天擋掉 |

楽天這一項一定要用結構判斷、不能比對文字：進度列最後一步的**名稱**就叫「配達完了」，
包裹還在路上時那四個字照樣顯示在畫面上，比對文字會把每一筆都當成已送達。

Amazon 則相反，只有文字可用 —— 整個包裹區塊裡沒有任何標示送達狀態的 class 或屬性。
所以只比對**實際看過的三個語系**的字樣；簡體中文要連「已」一起比對，
因為在途顯示的是「预计…送达」，只比「送达」會把在途的也濾掉。

**判斷不出來時一律保留。** 漏掉一個還在路上的包裹，比多出一筆已送達的嚴重。目前有五個判斷不到的地方：

- **楽天的英文介面**沒有配送進度列（列表頁連配送資訊都沒有），擋不掉已送達的。要過濾請用日文或繁中介面
- **Shopify** 的訂單狀態只到「已出貨」（fulfilled），站台本身就不知道包裹有沒有送達。
  ちいかわマーケット 與 jypj-store 的 fixture 都是出貨兩個月以上才擷取的，頁面上一樣只有「発送済」
- **ポケモンセンター** 的進度最多到「発送済み」。fixture 裡出貨一年多的訂單，列表頁上也還是「発送済み」
- **plusmember** 的詳細頁最多到「発送完了」。fixture 裡 5 月出貨的訂單，詳細頁上也還是「発送完了」
- **ちいかわくじ** 的狀態最多到「発送されました」。fixture 裡 2025 年 5 月寄出的包裹，現在也還是「発送されました」

這五個都是**站台本身就沒有這筆資料**，不是解析沒做到。目前先這樣，已送達的會混進這五個的結果裡。

## 輸出格式

**一個包裹一筆**：同一筆訂單有多個包裹（多個伝票番号）時，注文番号與合計會重複出現。

```json
[
  {
    "orderId": "297942-20260918-0695404827",
    "orderedAt": "2026-09-18",
    "total": 10660,
    "currency": "JPY",
    "carrier": "ヤマト運輸",
    "trackingId": "391175086374",
    "items": [
      { "title": "ヤマサ 醤油 …", "quantity": 1, "imageUrl": "https://thumbnail.image.rakuten.co.jp/…jpg" }
    ]
  }
]
```

| 欄位 | 說明 |
| --- | --- |
| `orderId` | 注文番号 |
| `orderedAt` | 注文日（`YYYY-MM-DD`）。讀不到時為空字串 |
| `total` | 整筆訂單的合計（不是這個包裹的）。讀不到時為 `null` |
| `currency` | 固定 `JPY` |
| `carrier` / `trackingId` | 配送業者 / 伝票番号。伝票番号去掉連字號（ポケモンセンター頁面上是 `5040-1844-1522`，業者查詢網址用的是 `504018441522`）。讀不到時為空字串 |
| `items[].title` / `imageUrl` | 品名 / 商品圖 |
| `items[].quantity` | 数量。沒有標示就是 1 |

- Amazon、mu-mo、ZOZOTOWN 知道哪件商品在哪個包裹，所以商品會分到各自的包裹下
- ZOZOTOWN 的「まとめて発送」是好幾筆訂單合併成一個包裹：每筆訂單各一列、伝票番号相同、商品只放那筆訂單自己的
- 楽天、ポケモンセンター、にじさんじ、アニメイト不標示商品與包裹的對應，所以同一筆訂單的商品會掛在它的每個伝票番号下
- にじさんじ與 ZOZOTOWN 的頁面上沒有配送業者，`carrier` 一律是空字串
- plusmember 一筆訂單只看過一個お問い合わせ番号，商品都掛在那個包裹下
- ちいかわくじ 是抽完之後另外申請配送，一次配送可以包含好幾次購入的獎品，所以 `orderId` 是配送情報的**引き換え番号**（不是購入番号），一個包裹一列。
  `orderedAt` 是購入日時，`total` 是這個包裹裡那幾次購入的購入金額加總（不含配送料），`carrier` 照頁面寫的「佐川急便 宅配便」

### Amazon 的錨點

外層卡片的 class 最常改版，所以以穩定元素當錨點，再往上找出所屬範圍（`climbUnique`）：

| 欄位 | 錨點 |
| --- | --- |
| 訂單範圍 / 注文番号 | `.yohtmlc-order-id`。同一個番号在桌機 / 手機標頭可能各出現一次，所以算的是「不同的番号」 |
| 合計 | `.order-header__header-list-item` 內的「合計 / Total / 总价」標籤；認不得標籤時取標頭裡第一個含金額的欄位 |
| 是否配送中 | 包裹內要有 `a[href*="/progress-tracker/package"]`（配送状況を確認按鈕），且 `.yohtmlc-shipment-status-primaryText` 不是已送達的字樣 |
| 品名 / ASIN | `a[href*="asin_title"]`（退回：任何帶文字的 `/dp/` 連結、`.yohtmlc-product-title` 純文字、商品圖 `alt`） |
| 圖片 | `img[alt=品名]`，優先取 `data-a-hires` |
| 数量 | 該圖片所屬 `.product-image` 裡的 `.product-image__qty`。只有 2 件以上才顯示，沒有就是 1 件。**只從自己那張圖找**，避免借到同包裹其他商品的數量 |
| 配送業者 / トラッキングID | 配送狀況頁的標題「配送業者 / Shipped with / 由 X 配送」與 `.pt-delivery-card-trackingId` |

### Shopify 的錨點

版面依據 [Dawn](https://github.com/Shopify/dawn)（Shopify 官方開源佈景主題）的
`sections/main-account.liquid` 與 `main-order.liquid`。

關鍵：**Dawn 用 `id` / `headers` 屬性標示欄位，這些屬性不會被翻譯**，
所以多語系完全不必比對字樣。其他佈景主題可能改過版面，因此每個欄位都再退一層結構判斷。

| 欄位 | 錨點 |
| --- | --- |
| 訂單頁判斷 | 路徑是 `/account`，可帶語系前綴（`/zh-hant/account`、`/zh-hans/account`…）。前綴不一定是兩個字母 |
| 訂單範圍 / 注文番号 | `a[href*="/account/orders/"]`（任何佈景主題都有），往上爬到 `<tr>` |
| 合計（列表頁，可能沒有） | `td[headers~="ColumnTotal"]`；退回時要求該欄位含幣別標記（`¥` / `JPY` / `円`），否則日期欄的「2024年12月28日」會被當成金額 2024 |
| 合計（詳細頁，優先） | `td[headers~="RowTotal"]` → class 含 `order_total` / `order-total` 的元素 → 表尾最後一個金額。都避開小計 / 送料 / 稅 |
| 品名 | 該列的 `a[href*="/products/"]`，沒有連結時退回該列的標題元素（`h1`–`h5`） |
| 数量 | `td[headers~="ColumnQuantity"]` → class 含 `qty` / `quantity` 的欄位 → 整格只有數字的欄位 |
| 配送業者 / 追蹤番号 | 文字剛好是 `{{ tracking_company }} #{{ tracking_number }}` 的最內層元素。`#` 是樣板寫死的字元，不是翻譯，所以可以直接當錨點 |
| 下一頁 | 佈景主題畫的分頁連結，沒有的話把網址的 `?page=N` 加一。加過頭也不會有事：回來的是空頁或同一頁，掃描端發現沒有新的注文番号就停 |
| 画像 | 該列若有 `<img>` 就直接用（去掉 Shopify CDN 的 `_100x` 尺寸後綴）。沒有才用商品連結的路徑加 `.js` 取 `featured_image`，保留語系前綴避免轉址。同一件商品只問一次 |

訂單列表只有注文番号 / 日期 / 狀態 / 合計，所以**目前這一頁上的每筆訂單都要讀一次詳細頁**。
那些頁面是伺服器渲染的，用 `fetch` 就夠，不必開 iframe。

列表上的「発送状況」欄看得出未出貨 / 部分出貨 / 已出貨，但**那是翻譯過的字樣**（`headers` 屬性只標欄位、不帶原始值），
所以不拿它來跳過詳細頁 —— 認錯一個就會漏掉一筆真的出貨了的訂單，代價比多讀幾頁大得多。

**部分出貨**時同一張訂單裡有的商品有配送資訊、有的沒有，只輸出出了貨的那些；
`total` 仍是整筆訂單的合計（輸出格式本來就是「一個包裹一筆，合計重複出現」）。

實際看過的兩種佈景主題差很多，所以解析**不靠固定的表格選擇器**：

| | ちいかわマーケット（Dawn 原版） | jypj-store（客製） |
| --- | --- | --- |
| 欄位標示 | `id` / `headers` 屬性 | 沒有，用 class |
| 品名 | `a[href*="/products/"]` | `<h4>`（沒有商品連結） |
| 商品圖 | 沒有 → 另外要商品 JSON | 訂單頁上就有 `<img>` |
| 追蹤號 | `<span>` 裡 | 追蹤連結的 `<a>` 裡 |
| 合計 | 表尾 `td[headers~="RowTotal"]` | `<dl class="order_total">` |
| 列表頁合計欄 | 有（`5,940.00JPY`） | **沒有** |

共通點只有一個：配送資訊一律輸出「`{{ tracking_company }} #{{ tracking_number }}`」。
所以改以那個 `#` 為錨點找出配送資訊，再往上找出它所屬的那一列，其餘欄位都在那一列裡找。

### 楽天的錨點

樂天的 class 帶雜湊（`ellipsis--3QFZf`），雜湊每次改版都會變，所以只比對前綴（`[class*="ellipsis--"]`）：

| 欄位 | 錨點 |
| --- | --- |
| 訂單範圍 / 注文番号 | 內容剛好是 `123456-20260929-0083907767` 的 `span`，再往上爬 |
| 品名 / 圖片 | 商品連結 `a[href*="item.rakuten.co.jp"]` 裡的 `img`，品名取 `alt`，圖片去掉 `?_ex=` 尺寸參數。商店 logo 連的是 `www.rakuten.co.jp`，所以不會被當成商品 |
| 数量 | 列表頁沒有。詳細頁每件商品一個「数量：/ Quantity: / 數量：」標籤，往上爬到只含這一件商品的範圍取品名當對照鍵，再回填到列表頁的商品；對不上就當 1 件 |
| 是否擷取 | 列表頁有沒有伝票番号（出貨狀態區塊 `[class*="shipping-status--"]`），以及該區塊的進度列是不是停在最後一步（已送達）。看得出來不用擷取時，連詳細頁都不會載入 |
| 注文詳細頁 | `a[href*="act=detail_page_view"]`，找不到時用注文番号自行組出 |
| 合計 | 詳細頁「支払い金額 / Total amount / 付款金額」標籤旁的金額（避開小計 / 送料）；認不得標籤時取字最大的金額 |
| 配送業者 / 伝票番号 | 列表頁或詳細頁「配送業者 / Shipping company / 物流業者」「伝票番号 / Tracking number / 運單號」標籤旁的值 |

英文介面的**列表頁沒有配送資訊**（連出貨進度都沒有），所以英文介面一定要載入詳細頁才知道有沒有伝票番号。

認不得標籤時（其他語系）還有一條後備規則：抓**出貨狀態區塊內**連到業者查詢頁的外部連結，
`aria-label` 當業者名，伝票番号必須是某個**查詢參數的完整值**（例如 `?oku01=568506023470`）。
同一個伝票番号有好幾個連結時只算一個包裹、業者名取第一個 —— 繁中詳細頁的「變更取件地點與時間」按鈕
跟業者名稱連到同一個黑貓查詢網址，不去重就會多出一個業者叫「變更取件地點與時間」的假包裹（第 18 項）。

> 這條規則限制得很嚴是有原因的。頁面上的活動連結（例如「○倍の注意点」）同樣是
> 「外部網域 + 有 `aria-label` + 網址帶長數字」，不限制範圍就會被當成配送業者，
> 產生假的伝票番号（實際發生過：`○倍の注意点 / 000031092`）。
> 這批資料會進 WMS，抓錯比抓不到更糟。回歸測試在 [rakuten.test.cjs](tests/rakuten.test.cjs) 第 8 項。

### タワーレコードの錨點

列表頁上什麼都有，所以這個轉接層**不回報任何要另外讀的頁面**（`lookups: []`）。

| 欄位 | 錨點 |
| --- | --- |
| 訂單頁判斷 | 網域是 tower.jp、路徑在 `/ec/` 底下，而且頁面上有 `.deliveryBox` 裡的「注文番号」標籤。認版面特徵不認固定網址 |
| 配送範圍 | 一個 `.deliveryBox` 就是一次配送（注文番号旁的「配送1」就是這個意思） |
| 注文番号 / 合計 | `.deliveryAbout` 裡「注文番号」「注文合計」標籤（`td.ttl`）同一列的下一格。注文番号要去掉後面的 `.dlvrIcon`（「配送1」） |
| 品名 / 画像 | `.deliveryItemBox` 裡的 `.title a` 與 `.deliveryThum img`（品名讀不到時退回圖片的 `alt`） |
| 数量 | `.ship-num` 裡的數字，沒有就看商品明細 `.pDetail` 的「￥1,650　数量：1」，再沒有就當 1 件 |
| 是否配送中 | 出荷表示 `.deliverySt` 裡沒有「受取済」。送達後會變成「…に出荷しました（受取済）」 |
| 伝票番号 | `.deliveryRightClm` 裡連到業者查詢頁的**絕對網址**連結，連結文字就是番号（同一區塊的「領収書」是站內相對路徑，不會被選到） |
| 配送業者 | 由上面那個查詢網址的網域判斷（japanpost / kuronekoyamato / sagawa-exp）。認不得就留空，但伝票番号仍保留 |

**配送業者不能讀頁面上的「配送業者」欄位** —— 那是下單時的指定，實際頁面上寫的是「指定なし」。

同一筆訂單分批出貨時會有多個 `.deliveryBox`，轉接層會依注文番号把它們併成一筆訂單、
每個 `.deliveryBox` 各自是一個包裹。**不能分開回傳** —— `main.js` 會依注文番号去重，會吃掉一筆。

### ポケモンセンターの錨點

Salesforce Commerce Cloud 的站台（素材路徑是 `/on/demandware.static/`），頁面是伺服器渲染的 ——
HTML 裡有伺服器輸出的 `dwMarker` 註解。所以注文詳細頁用 `fetch` 讀，不開 iframe。

| 欄位 | 錨點 |
| --- | --- |
| 訂單頁判斷 | 網域是 pokemoncenter-online.com，而且 `.comOrderList` 裡有 `a[href*="/order-details/"]`。不看路徑 |

### 另外載入的頁面

Amazon 的配送狀況頁與楽天的注文詳細頁都是前端渲染，`fetch` 只拿得到空殼，必須讓瀏覽器真的載入。
（Shopify、ポケモンセンター、にじさんじ、mu-mo、ZOZOTOWN、plusmember 的頁面是伺服器渲染的，直接 `fetch`，這一節的限制都不適用。
`fetch` 回來的頁面照 `Content-Type` 的 charset 解碼，沒寫就看 `<meta charset>`，再沒有才當 UTF-8 ——
`res.text()` 一律當 UTF-8，Shift_JIS 之類的舊站會變成亂碼。E2E 有一個站台故意用 Shift_JIS 回應來驗證這件事。）

**只用隱藏 iframe**：在目前頁面內用看不見的 iframe 載入（同網域，可直接讀 DOM），反覆讀到欄位出現為止
（上限 15 秒；只出現部分欄位時再等 2 秒）。不開新分頁、不需要背景程式，分頁列不會閃。
iframe 設了 `sandbox`（不給 `allow-top-navigation`），對方頁面的防嵌入程式無法把目前頁面導走。

被擋下時就**放棄那一頁**，相關欄位留空，不會另開分頁硬讀。

ちいかわくじ的兩頁連網址都拿不到，是在 iframe 裡**點過去**的：iframe 載入購入履歴之後，點卡片、點按鈕都由頁面自己的程式換頁（`history.pushState`），
同一份文件裡等新內容畫出來再讀（一樣是上限 15 秒、部分欄位再等 2 秒）。

樂天的購買履歷頁會回 `x-frame-options: DENY`，所以 [rules.json](rules.json) 是**必要的**，不是最佳化 —
少了它，樂天的合計就抓不到。規則用 `declarativeNetRequest` 在**子框架請求**上移除這個標頭，
條件限定「由購買履歷頁發起、且指向購買履歷頁」，只影響本擴充功能自己載入的那個 iframe，正常瀏覽不受影響。
Amazon 的配送狀況頁目前沒有這個標頭，也加了一條預防性的規則。

所有要讀的頁面同時進行，且 HTML 解析完就開始讀，不等圖片載完。

## 多語系

只比對**實際出現過**的字樣，不做其他語言的推測。Amazon 支援日本語 / English / 简体中文，楽天支援日本語 / English / 繁體中文，ポケモンセンター、にじさんじ、アニメイト、mu-mo、ZOZOTOWN、plusmember、ちいかわくじ 只看過日文頁面。

Amazon 各語系的實際字樣（同一筆訂單）：

| | 合計 | 配送業者 | トラッキングID |
| --- | --- | --- | --- |
| 日本語 | `合計` `￥2,322` | `配送業者 日本郵便` | `トラッキングID: 421304890904` |
| English | `Total` `¥2,322` | `Shipped with 日本郵便` | `Tracking ID 421304890904` |
| 简体中文 | `总价` `JP¥2,322` | `由日本郵便配送` | `追踪编码 421304890904` |

處理方式（見 [sites/amazon.js](src/content/sites/amazon.js) 的 `TOTAL_LABEL_RE`、[readers.js](src/content/readers.js) 的 `CARRIER_*` / `TRACKING_LABEL_RE`）：

- **標籤字樣**不依賴冒號（英文、簡體中文都沒有冒號）
- **配送業者**支援「標籤在前」（`Shipped with X`）和「前後包住」（`由 X 配送`）兩種寫法
- **金額**接受 `￥` / `¥` / `JP¥`
- 認不得標籤時的後備規則（不依賴語言）：合計取標頭裡第一個含金額的欄位；トラッキングID 取最後一段像編號的字串

楽天各語系的實際字樣。版面完全一樣，只換標籤文字，所以只要把標籤加進
[sites/rakuten.js](src/content/sites/rakuten.js) 的 `LABELS` / `ID_LABEL_RE` 與
[readers.js](src/content/readers.js) 的 `RAKUTEN_LABELS`：

| | 注文番号 | 注文日 | 配送業者 | 伝票番号 | 合計（詳細頁） | 数量（詳細頁） |
| --- | --- | --- | --- | --- | --- | --- |
| 日本語 | `注文番号：` | `注文日：` | `配送業者` | `伝票番号` | `支払い金額` | `数量：` |
| English | `Order number` | `Order date` | `Shipping company` | `Tracking number` | `Total amount` | `Quantity` |
| 繁體中文 | `訂單編號：` | `訂單日期：` | `物流業者` | `運單號` | `付款金額` | `數量：` |

日文與繁中的列表頁同一批訂單各存了一份 fixture，測試要求兩份讀到一模一樣的結果。

```sh
npm run e2e                         # 一般情況
XFO_DENY=1 npm run e2e              # 站台回 x-frame-options: DENY → rules.json 應讓 iframe 仍可用
NO_DNR=1 XFO_DENY=1 npm run e2e     # 不套用 rules.json → iframe 真的被擋下，相關欄位應留空
```

E2E 會把整個擴充功能複製一份到暫存目錄、把網域換成 localhost 再載入 Chrome，所以不會動到工作目錄。
它用擴充功能自己的 popup 頁當驅動（沒有 service worker 可用了），並檢查**全程沒有另開分頁**。

## 已知限制

- 自動翻頁只有 **Shopify** 用實際網址驗證過（`?page=N`）；**アニメイト**（「次へ>>」）與 **ZOZOTOWN** 的分頁區塊取自實際頁面。
  **楽天翻不了** —— 它的「次へ」是 `<button>` 沒有連結（整頁是前端渲染的 SPA），得在頁面裡按那顆按鈕才會換頁，還沒做。
  **Amazon、タワーレコード、ポケモンセンター、にじさんじ、plusmember** 走的是通用規則（`rel="next"` / 連結文字是「次へ」之類），
  但手上的實際頁面都被裁掉了分頁區塊，所以沒驗證過 —— 認不出來就停在目前這一頁，不會出錯只是不會翻
- Shopify 與 plusmember 的訂單列表看不出哪些訂單有追蹤號，所以**七天內的**每筆訂單都要各讀一次詳細頁
- 七天看的是**注文日**，不是出貨日。預購商品下單很久之後才出貨（アニメイト 實際看過：8/25 下單、10/14 寄出），
  這種包裹在路上時注文日早就超過七天，不會列出來。ちいかわくじ也一樣（看購入日時），而且幾乎每一筆都是這樣
- ちいかわくじ 點卡片、點按鈕的流程只在 E2E 的模擬頁面上跑過（照實際頁面的結構造的），實際站台還沒驗證。
  也假設列表是新到舊排的（跟其他站台一樣）。只看目前畫在頁面上的卡片，沒有翻頁；
  一次購入有好幾個配送時只點第一個「配送情報を見る」（實際只看過一個）
- にじさんじ的列表帶 `data-show-init="12"`，看起來一次只顯示 12 筆、其餘要按按鈕載入。那個按鈕還沒看過：
  如果其餘的訂單已經在 HTML 裡只是先藏起來，照樣讀得到；如果是按了才去要，就只讀得到前 12 筆
- mu-mo 的配送中字樣還沒看過，所以「不是出荷待ち / 配達完了」的都會讀詳細頁。分頁也還沒看過（走通用規則）。
  `jumpdetail` 表單的實際內容沒拿到，測試裡的表單是照 `detail()` 的原始碼造的，POST / GET 兩種都驗
- ZOZOTOWN 一筆訂單分成好幾個包裹、而且詳細頁有好幾個伝票番号時，分不出哪個號碼對哪個包裹，
  每個號碼都會掛上那筆訂單所有沒送達的商品（實際頁面上只看過一個伝票番号）
- plusmember 的 `fnChangeAction` / `fnKeySubmit` 原始碼與那張表單都沒拿到，測試裡的表單是造的，POST / GET 兩種都驗。
  列表頁的實際網址也還沒看過（只影響 `./history.php` 怎麼解析，測試用 `/shop/mypage/index.php`）。
  お問い合わせ番号只看過一個，一筆訂單有好幾個號碼時的寫法還不知道
- 只擷取**配送中**的包裹。楽天的英文介面、Shopify、ポケモンセンター、plusmember、ちいかわくじ 讀不到送達狀態，已送達的會混進來（見「只擷取配送中的訂單」）
- 只解析訂單列表頁與配送狀況頁 / 注文詳細頁，不會讀配送先住所、支付方式、單價
- 另外載入的頁面一律走隱藏 iframe。站台若擋住嵌入（`x-frame-options` / `content-security-policy: frame-ancestors`）
  且 [rules.json](rules.json) 沒涵蓋到，那一頁就讀不到，相關欄位留空
- 需要本人登入狀態。被導到登入頁時會中止並顯示訊息
- 解析依賴站台的 DOM 結構，改版可能失效。先跑 `npm test`，必要時把新的實際頁面放進 `tests/fixtures/` 再修
